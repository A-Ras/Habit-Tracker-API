# 🔧 Änderungsprotokoll – 08.09.2026

Behebung des Docker-Fehlers:

```
Error response from daemon: failed to set up container networking: driver failed
programming external connectivity on endpoint habit-api (...):
Bind for 0.0.0.0:8000 failed: port is already allocated
```

---

## 1. Ursachenanalyse

Bei der Fehlersuche wurden **zwei** Probleme gefunden:

### Problem 1: Port 8000 war belegt (ursprünglicher Fehler)

Ein **alter Container `habit-app`** aus einer früheren Version des Projekts lief noch
und belegte Port 8000. Der neue Compose-Container `habit-api` konnte deshalb nicht
starten und blieb im Status `Created` hängen.

Vorhandene Container vor der Bereinigung:

| Container       | Status            | Ports          | Bemerkung                          |
|-----------------|-------------------|----------------|------------------------------------|
| `habit-app`     | Up                | 8000 → 8000    | ❌ Alter Container – blockierte Port 8000 |
| `habit-api`     | Created (gestoppt)| –              | Neuer Container, Start schlug fehl |
| `habit-postgres`| Up (healthy)      | 5432 → 5432    | OK                                 |
| `postgres_db`   | Exited (13 Tage)  | –              | Gehört zu anderem Projekt – **bewusst nicht angerührt** |

### Problem 2: App stürzte nach dem Start ab (zweites Problem)

Nach dem Entfernen des alten Containers startete `habit-api`, stürzte aber mit
folgendem Fehler ab:

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
database_url
  Extra inputs are not permitted [type=extra_forbidden, ...]
```

**Grund:** Das `Settings`-Modell in `app/config.py` definierte nur die Felder
`secret_key`, `algorithm` und `access_token_expire_minutes`. Pydantic-Settings
lehnt standardmäßig alle *unbekannten* Umgebungsvariablen ab
(`extra="forbidden"` ist der Default). Die Variable `DATABASE_URL` aus der
`.env` bzw. aus `docker-compose.yml` wurde deshalb als "extra input" abgelehnt.

Die Datenbank-URL wird ohnehin **nicht** über `Settings` gelesen, sondern
separat in `app/database.py`:

```python
DATABASE_URL = os.getenv(
    "DATABASE_URL",
    "sqlite:///./db/habit_tracker.db"  # Fallback für lokale Entwicklung ohne Docker
)
```

## 2. Durchgeführte Änderungen

### 2.1 Docker-Bereinigung (keine Dateiänderung)

```powershell
docker rm -f habit-app   # alten Container entfernt – Port 8000 wieder frei
```

> Der Container `postgres_db` des anderen Projekts wurde **nicht** gelöscht.

### 2.2 Dateiänderung: `app/config.py`

**Vorher:**

```python
model_config = SettingsConfigDict(env_file=".env")
```

**Nachher:**

```python
model_config = SettingsConfigDict(
    env_file=".env",
    extra="ignore",  # z.B. DATABASE_URL wird in app/database.py separat gelesen
)
```

**Erklärung:** Mit `extra="ignore"` ignoriert das `Settings`-Modell zusätzliche
Umgebungsvariablen (z. B. `DATABASE_URL`), statt mit einem
`ValidationError` abzustürzen. Das Verhalten von `app/database.py`
(`os.getenv("DATABASE_URL")`) bleibt unverändert.

## 4. Offene Punkte / Hinweise

### 4.1 Duplicate Operation IDs (kosmetisch, kein Fehler)

Beim Generieren der OpenAPI-Docs erscheinen Warnungen aus `app/routers/tasks.py`:

```
UserWarning: Duplicate Operation ID update_task_tasks__task_id__patch for function update_task
UserWarning: Duplicate Operation ID delete_task_tasks__task_id__delete for function delete_task
```

Es gibt also doppelte Routen für `PATCH /tasks/{task_id}` und
`DELETE /tasks/{task_id}`. Die API funktioniert trotzdem (FastAPI nutzt die
erste gefundene Route), aber die doppelten Routen sollten aufgeräumt werden.

### 4.2 Potenzialer Port-Konflikt mit dem anderen Projekt

Der gestoppte Container `postgres_db` (anderes Projekt) nutzt ebenfalls
Port 5432. Sobald dieses Projekt wieder gestartet wird, gibt es denselben
Fehler wie oben – nur mit Postgres:

```
Bind for 0.0.0.0:5432 failed: port is already allocated
```

**Lösung:** In der `docker-compose.yml` des anderen Projekts einen anderen
Host-Port verwenden, z. B. `"5433:5432"`.
