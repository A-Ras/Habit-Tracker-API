## 1. Ursachenanalyse

Bei der Fehlersuche wurden **drei** Probleme gefunden:

### Problem 1: Lokales PostgreSQL blockierte Port 5432 (ursprünglicher Fehler)

Auf dem Rechner läuft ein **lokal installierter PostgreSQL-18-Server**
(`postgresql-x64-18`, Windows-Dienst, Status: *Running*), der Port **5432** belegt.
Die Alembic-Verbindung nach `localhost:5432` landete deshalb beim **lokalen**
Postgres statt beim Docker-Container `habit-postgres`.

Der Docker-Container selbst war völlig in Ordnung:

| Prüfung                                     | Ergebnis                                            |
|---------------------------------------------|-----------------------------------------------------|
| Container `habit-postgres`                   | ✅ Up (healthy)                                      |
| Zugangsdaten im Container (`psql` per `docker exec`) | ✅ funktioniert                              |
| Fehlgeschlagene Anmeldungen in Container-Logs | ❌ keine Einträge → Verbindungen erreichten den Container **gar nicht** |

Die Server-Fehlermeldung lautete (aufgedeckt über einen Testzug mit **psycopg v3**,
da psycopg2 den Fehler verschluckt – siehe Problem 2):

```
FATAL: Passwort-Authentifizierung für Benutzer »habituser« fehlgeschlagen
```

### Problem 2: psycopg2 verschluckt die echte Fehlermeldung unter Windows

`psycopg2` brach mit folgendem Fehler ab, statt die eigentliche Meldung zu zeigen:

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfc in position 97: invalid start byte
```

**Grund:** Unter Windows liefert libpq Fehlermeldungen des lokalen Servers in der
ANSI-Codepage des Systems (hier CP1252 – `0xfc` = `ü` in »für Benutzer«).
psycopg2 versucht, diese Meldung als UTF-8 zu dekodieren und stürzt dabei ab.
Das eigentliche `OperationalError` geht verloren. → Bekanntes psycopg2-Problem
unter Windows mit nicht-englischem Gebietsschema.

### Problem 3: `alembic/env.py` überschrieb `target_metadata` mit `None`

In `alembic/env.py` wurde `target_metadata` zwar am Dateianfang korrekt gesetzt,
aber in Zeile 22 durch das Alembic-Standardtemplate wieder überschrieben:

```python
target_metadata = Base.metadata   # korrekt
...
target_metadata = None            # ❌ überschreibt alles → Autogenerate findet nie Änderungen
```

Zusätzlich: Das Verzeichnis `alembic/versions/` war **leer** – es existierte keine
einzige Migration. Die Tabellen in der DB waren per `Base.metadata.create_all()`
entstanden, nicht über Alembic.

### 2.4 Baseline-Migration erstellt

Da `alembic/versions/` leer war, wurde eine echte **Baseline-Migration**
autogeneriert. Vorgehen:

1. Temporäre leere Datenbank `habittracker_empty` im Container angelegt
2. `alembic revision --autogenerate -m "initial schema"` **gegen die leere DB**
   ausgeführt → Migration enthält echte `CREATE TABLE`-Statements
3. Temporäre Datenbank wieder gelöscht
4. Da die bestehende DB die Tabellen bereits hat (aus `create_all()`), wurde sie
   mit `alembic stamp head` als „bereits migriert" markiert – **ohne Datenverlust**

**Neue Datei:** `alembic/versions/c2fd8687cd12_initial_schema.py` (Revision `c2fd8687cd12`)

Enthält die Tabellen: `users`, `projects`, `habits`, `tasks`, `habit_check_ins`
(inkl. Indizes und Fremdschlüssel-Constraints).

## 5. Nachtrag (gleicher Tag): Fehler `relation "users" already exists`

### Ursache

Nach einem Neustart der Container (frisches DB-Volume) schlug
`uv run python -m alembic upgrade head` erneut fehl:

```
psycopg2.errors.DuplicateTable: relation "users" already exists
```

**Grund:** `app/main.py` führte beim **jedem** App-Start aus:

```python
models.Base.metadata.create_all(bind=engine)
```

Der API-Container startete → `create_all()` legte die 5 Tabellen **ohne**
`alembic_version`-Eintrag an → Alembic versuchte daraufhin, die Baseline-Migration
auszuführen und stieß auf bereits existierende Tabellen.

### Behobene Änderungen

**`app/main.py`** – `create_all()` entfernt (Schema-Verwaltung gehört jetzt
ausschließlich zu Alembic):

```diff
- from app import models
- from app.database import engine
  from app.routers import users, projects, tasks, habits, auth
...
- models.Base.metadata.create_all(bind=engine)
```

**`docker-compose.yml`** – API-Container führt Migrationen vor dem Serverstart aus
(funktioniert auch bei komplett frischem DB-Volume):

```diff
    depends_on:
      db:
        condition: service_healthy
+   command: >
+     sh -c "uv run python -m alembic upgrade head &&
+            uv run python -m uvicorn app.main:app --host 0.0.0.0 --port 8000"
```

**`alembic/env.py`** – `DATABASE_URL` aus der Umgebung hat Vorrang vor `alembic.ini`
(nötig, da die DB im Docker-Netzwerk unter `db:5432` und auf dem Host unter
`localhost:5433` erreichbar ist):

```python
import os

database_url = os.getenv("DATABASE_URL")
if database_url:
    config.set_main_option("sqlalchemy.url", database_url)
```

Die bestehende Datenbank wurde erneut per `alembic stamp head` mit der Revision
`c2fd8687cd12` synchronisiert.

## 6. Nachtrag (gleicher Tag): Image-Name `habit-tracker-api-api` bereinigt

### Ursache

Docker Compose setzt den Image-Namen aus **Projektname + Service-Name** zusammen.
Ohne explizite Angabe leitet sich der Projektname aus dem Verzeichnisnamen ab
(`habit-tracker-api`), der Service heißt `api` → Image `habit-tracker-api-api`.

### Behobene Änderungen (`docker-compose.yml`)

```diff
- version: "3.8"
+ # Expliziter Projektname (sonst leitet Compose ihn aus dem Verzeichnisnamen ab
+ # und der Image-Name würde doppelt "habit-tracker-api-api" lauten)
+ name: habit-tracker

  api:
    build: .
+   # Eigener Image-Name (statt automatisch generiertem "habit-tracker-api-api")
+   image: habit-tracker-api:latest
    container_name: habit-api

  volumes:
    postgres_data:
+     # Bestehendes Volume des alten Projektnamens weiterverwenden (Datenerhalt!)
+     external: true
+     name: habit-tracker-api_postgres_data
```

**Anmerkungen:**

- Das veraltete `version:`-Feld wurde entfernt (Compose 2 warnt seit langem
  danach, der Wert wird ignoriert).
- Durch den neuen Projektnamen `habit-tracker` würde Compose ein **neues, leeres
  Volume** (`habit-tracker_postgres_data`) anlegen. Damit die bestehenden Daten
  (registrierter User!) erhalten bleiben, wurde das alte Volume
  `habit-tracker-api_postgres_data` per `external: true` + `name:` explizit
  weitergebunden.
- Die alten Container (`habit-postgres`, `habit-api`) mussten für den
  Projektwechsel einmalig entfernt und neu erstellt werden – die Daten lagen
  sicher im Volume.
- Das alte Image `habit-tracker-api-api:latest` wurde entfernt.
